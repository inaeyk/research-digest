## Distribution architecture

```text
exact v0.4.1 GitHub Release
  |-- SHA256SUMS
  |-- platform entry point
  |-- standard-library installer core
  `-- exact universal wheel
             |
             v
new inactive runtime/0.4.1/venv
             |
    version + doctor + UI-status checks
             |
             v
existing owned schedule repointed
             |
             v
atomic runtime state records updated
             |
             v
owned launcher atomically repointed
```

The shared installer core holds download integrity, runtime ownership,
installation, verification, activation, and uninstall safety. Shell and
PowerShell contain only platform discovery and delegation. Research Digest
business logic is not duplicated in either wrapper.

Exact private runtime roots:

- macOS: `~/Library/Application Support/Research Digest/runtime/`
- Windows/WSL: `~/.local/share/research-digest/runtime/`
- with an intentional `RESEARCH_DIGEST_DATA_DIR`, the runtime is its `runtime/`
  child, consistent with the existing application path policy.

Each version is installed at `<root>/<version>/venv/`. `current.json` and
`previous.json` are atomic, owned JSON records rather than symlinks, avoiding
Windows/WSL symlink assumptions. The thin macOS app and Windows shortcut point
to the exact versioned CLI. Runtime code is never installed in the app bundle.
Each version marker records the verified release-wheel SHA-256; a same-version
runtime is reused only when that digest matches the newly verified wheel.

## Release asset set

The explicit v1 set is:

2. `install-research-digest.py`
3. `install-research-digest-macos.sh`
4. `install-research-digest-windows.ps1`
5. `SHA256SUMS`

The small shared Python asset is justified because it keeps integrity,
ownership, transaction, verification, migration, and uninstall behavior single
sourced across platforms. It uses only Python's standard library. The platform
wrappers verify this core against `SHA256SUMS`; the core separately verifies the
exact wheel before creating a versioned runtime.

GitHub-generated source archives remain contributor artifacts. They are not the
recommended ordinary-user installation.

## Installation, migration, and rollback behavior

The installer:

1. rejects unsupported platforms and Python before creating a runtime;
2. obtains the exact v0.4.1 manifest and wheel;
3. rejects malformed, duplicate, path-bearing, missing, or mismatched hashes;
4. creates only a previously absent `runtime/0.4.1/` directory;
5. installs the wheel into its private venv;
6. runs `--version`, `doctor`, and `ui-status --json` without scientific work;
7. if and only if a schedule exists, validates ownership and preserves time and
   enabled/disabled state while repointing it;
8. atomically updates `current.json` and `previous.json`;
9. atomically repoints the owned launcher as the final activation operation.

Schedule and runtime-state changes are snapshotted and rolled back if a later
activation step fails. Scheduler snapshots preserve the exact owned launchd
plist or Windows Task Scheduler XML plus durable enabled and live loaded state;
rollback does not reconstruct an approximation. Both launcher backends build a
complete replacement before swapping their exact owned artifact. If rollback
itself cannot complete, activation fails closed with an explicit
incomplete-rollback diagnostic and retains the verified new runtime for manual
recovery.

A venv is constructed directly in its final new version path because Python
console-script shebangs make post-construction venv renames unsafe. The path is
not active until verification and transactional launcher/scheduler activation.
A failed new installation restores the prior schedule/runtime records and does
not overwrite the previous version, user
data, source checkout, or Codex login. One prior runtime record and all prior
version directories are retained; automatic old-runtime deletion is deferred.

Migration from `~/research-digest/.venv` or
`~/researchrepo/research-digest/.venv` does not modify or delete that checkout.
Persistent data and config remain separate. Users receive the exact private
runtime path and may remove an obsolete checkout manually after verification.

## Uninstall behavior

Normal uninstall preflights active digest and scheduler state, stops only the
owned UI, removes only the owned launcher and versioned runtime, and preserves
personal data/config. It refuses to delete a runtime beneath an installed
schedule unless `--remove-schedule` is explicit. It refuses unknown or symlinked
entries in the owned runtime root.

Destructive purge additionally requires the exact phrase:

```text
DELETE MY RESEARCH DIGEST DATA
```

The confirmation is validated before uninstall mutation. Purge is never the
default.

## Required human smoke: macOS

Perform only from the exact locally staged candidate assets; do not clone the
repository on the test account. Verify every staged byte against the candidate
`SHA256SUMS` before use.

1. Back up with the current application and record schedule enabled state/time.
2. Preserve Codex installation/authentication and personal Research Digest data.
3. Remove the old owned launcher/runtime through its safe uninstaller. Do not
   delete personal data or the developer checkout merely for this test.
4. If a checkout exists, move it out of the test user's home or use a clean test
   account so no runtime can resolve through it.
5. Confirm `codex login status` is authenticated.
6. Transfer the exact staged shared core, wheel, and `SHA256SUMS`; run the
   verified shared core with `install --asset-dir <staging-directory>`. No
   repository may be present. The exact macOS wrapper is covered separately by
   deterministic download/discovery/integrity tests before publication.
7. Confirm the app target is
   `~/Library/Application Support/Research Digest/runtime/0.4.1/venv/bin/research-digest`.
8. Open `~/Applications/Research Digest.app`; verify detached UI launch and no
   digest merely from opening.
9. Start a real Codex-backed digest, observe real Codex execution, close/reopen
   the browser, run `ui-stop`, reopen the app, and confirm reattachment.
10. Cancel in the application; confirm `CANCELLED`, null `run_lock`, and
    preserved completed coverage.
11. Enable daily automation, verify exact private-runtime `ProgramArguments`
    and non-secret Codex `PATH`, and exercise the owned LaunchAgent. A no-op with
    no uncovered source dates must not create History.
12. Log out/in or restart and repeat app/schedule launch to close the previously
    deferred macOS restart smoke.
13. Confirm no Research Digest source checkout was introduced by installation.

## Required human smoke: Windows 11 / WSL2

Use a safe time with no unrelated WSL worker that shutdown would disrupt.

1. Back up and record the existing Task Scheduler enabled state/time.
2. Preserve Codex installation/authentication and personal Research Digest data.
3. Confirm `codex login status` inside the intended WSL distribution.
4. Transfer the exact staged shared core, wheel, and `SHA256SUMS`, then invoke
   the verified shared core with `install --asset-dir <staging-directory>`
   inside the selected WSL distribution. Record the exact distribution. The
   PowerShell wrapper's selection, quoting, and delegation boundary is covered
   separately by deterministic tests before publication.
5. Confirm the shortcut targets the selected distribution and exact
   `~/.local/share/research-digest/runtime/0.4.1/venv/bin/research-digest`.
6. With no checkout available, double-click **Research Digest** and verify the
   detached UI and absence of installation-created scientific work.
7. Run a real Codex digest; close/reopen UI, reattach, cancel, and verify
   preserved coverage and null lock.
8. Verify Task Scheduler retained time and enabled/disabled state and runs the
   exact private command with a usable non-secret Codex path.
9. After confirming no unrelated WSL work is active, run `wsl --shutdown`, then
   double-click the shortcut and complete a real Codex-backed run. This closes
   the previously deferred cold-WSL smoke.
10. Confirm installation created no source checkout.

## Proposed v0.4.1 release procedure

No step below is authorized by this candidate task.

1. Start from a clean, reviewed master commit and rerun all deterministic gates.
2. Run `python scripts/build_release_assets.py --output dist` once from that
   exact commit.
3. Independently enumerate the wheel, verify isolated execution, and check all
   `SHA256SUMS` entries.
4. Transfer those exact local assets to the macOS and Windows/WSL test machines
   without a source checkout, verify `SHA256SUMS`, and complete both human smoke
   protocols above. Do not pretend unpublished `v0.4.1` GitHub URLs exist.
5. Record sanitized evidence; never commit raw personal paths, hostnames,
   credentials, or authentication material.
6. Obtain a fresh release audit over the exact qualified bytes and smoke
   evidence.
7. Only after explicit authorization, create/push the annotated `v0.4.1` tag on
   the reviewed commit, create the GitHub Release for that tag, and upload the
   already-qualified assets. Do not use `master` URLs in installers.
8. Verify published hashes and exact release installer URLs one final time. Do not move or
   rewrite `v0.4.0`.

## Published installation and first run

The tested checkout was cloned directly from the published tag:

```bash
cd "$HOME"
git clone \
  --branch v0.4.0 \
  --depth 1 \
  https://github.com/inaeyk/research-digest.git \
  research-digest
cd "$HOME/research-digest"
```

Because the shell-default Python was unsupported, this smoke selected the
known-compatible Homebrew interpreter explicitly:

```bash
RESEARCH_DIGEST_PYTHON=/opt/homebrew/bin/python3.12 \
  ./scripts/bootstrap_macos.sh
```

The bootstrap completed and produced `research-digest 0.4.0`. The normal
documented path remains `./scripts/bootstrap_macos.sh`, which searches
compatible Python 3.11-or-newer candidates automatically; the override is a
troubleshooting fallback and its actual path is machine-dependent.

Before normal application initialization, `research-digest doctor` reported
`Failures: 0`. Its warnings were the expected clean-first-run state: config
file, data directory, SQLite database, schema, and schedule were not present;
no last run existed; and network checks were skipped.

After `research-digest status --json` initialized fresh state, it reported
schema `18`, config `5`, null `last_run`, null `run_lock`, and no installed
launchd schedule.

## Finder launcher and real Codex execution

`research-digest install-launcher` created
`~/Applications/Research Digest.app`, targeting
`~/research-digest/.venv/bin/research-digest`. Finder launch opened the default
browser, registered a macOS UI server at version 0.4.0 on port 8501, and did not
create a digest merely by launching.

A digest started from the Finder-launched application retrieved and stored 27
articles and preselected 11. A real `/opt/homebrew/bin/codex exec` process and
its native Darwin arm64 provider subprocess were observed. The run reached five
completed full analyses, qualifying the complete boundary:

```text
Finder -> Research Digest.app -> detached UI -> detached worker
       -> real Codex CLI -> Stage 1 and full analysis
```

## Lifecycle and cancellation

The clean-install smoke verified all of the following:

- Closing the browser left the digest `RUNNING`.
- Reopening **Research Digest.app** reattached to the same active run.
- `research-digest ui-stop` stopped only the UI; the digest continued.
- Relaunching restored the active run and its cancellation control.
- **Cancel digest** terminalized the run as `CANCELLED`.
- `run_lock` became null.
- Completed source coverage and completed work were preserved.
- Cancellation did not disable the installed schedule.

## launchd

Enabling **Automatic daily digest** installed the owned LaunchAgent at
`~/Library/LaunchAgents/org.research-digest.daily.plist` with backend `launchd`.
Its `ProgramArguments` were the installed
`~/research-digest/.venv/bin/research-digest` command followed by `run`, and its
PATH contained the actual Codex location. The plist contained no API keys,
ChatGPT tokens, or Codex authentication material.

The operator exercised the loaded job with:

```bash
launchctl kickstart -p \
  "gui/$(id -u)/org.research-digest.daily"
```

launchctl reported a spawned PID. The scheduler log then reported successful
Research Digest execution with zero succeeded or failed profiles and no
uncovered source dates. No `app_run` was created. This is the expected no-op
behavior: a scheduled invocation with no uncovered source dates may exit
normally without adding a History run.
